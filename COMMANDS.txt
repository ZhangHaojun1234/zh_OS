一、登录与提示符
--------------------------------------------------------------------------------
 内置账户:
   root   uid=0    gid=0    /root      管理员
   zh     uid=1000 gid=1000 /home/zh   普通用户
 两者初始密码都是 zh；useradd 新建账户的初始密码同样是 zh。

 账户持久化（B 组第 2 个功能）:
   账户表默认在内存中，重启即复位。若 QEMU 挂了一块可写磁盘
   （-drive file=disk.img,format=raw,if=ide），启动时 users_load() 会从
   LBA 200-207（8 扇区 / 4KB）读回账户表，useradd / passwd 成功后
   users_save() 立即写回，因此新增账户与改过的密码可跨重启保留。
   无磁盘（只 -cdrom 启动）时走内存态，useradd / passwd 会追加一行黄字
   [warn] disk read-only, changes lost on reboot。

 彩色提示符:
   [zh@zh_OS ~]$      普通用户
   [root@zh_OS ~]#    root
 分段颜色（Linux 红 / 黄 / 绿三色分级 + 默认浅灰）:
           用户名 root 红 / 普通绿，@ 浅灰，zh_OS 黄，~ 绿，
           结尾 # 或 $ 与用户名同色，方括号与空格浅灰。
   ~ 处显示的是 ramfs 的当前工作目录（cd 后立即变化）。

 键盘: 可打印 ASCII、左右 Shift、CapsLock、退格、回车，另有上/下箭头召回历史。
 密码输入回显 * ，不显示明文。

[1] help
    遍历 shell_command_table 打印命令名 + 英文说明，命令名绿、说明浅灰，
    末尾黄字提示 root 专属命令。新增命令只要追加到命令表，help 会自动带上。

[2] clear
    vga_clear() 清屏为浅灰字/黑底，光标回到左上角。

[3] echo [args...]
    把参数用单个空格连接后以绿输出；不带参数只输出一个空行。

[4] uname
    输出统一版本号字符串 "zh_OS 0.2beta (x86_64)"（亮绿）。
    该字符串来自 kernel/version.h，启动横幅 / 登录横幅 / GRUB 菜单同源。

[5] whoami
    输出当前登录用户名（亮绿）。未登录会话时输出红色错误。

[6] login
    在当前 Shell 内重走 login_screen()：清屏、绘制登录横幅、重新认证；
    成功后返回 Shell，提示符按新用户重新上色。

[7] logout
    打印 logout 后让 shell_run() 返回，由 kernel_main 重新进入登录流程。

[8] su [user]
    缺省切到 root。提示 Password: 并要求输入目标账户密码，
    认证成功打印 su: switched to <user>，下一轮提示符立即变色；
    失败打印红色 su: Authentication failure.

[9] useradd <name>
    仅 root 可用，普通用户执行会打印红色 Permission denied.
    uid/gid = 1000 + 当前账户数（第一个新账户是 1002），
    home 自动生成 /home/<name>，shell 为 /bin/zhsh，初始密码 zh。
    成功提示含 uid 与 default password: zh；有可写磁盘时紧接着落盘，
    无磁盘时追加黄字 [warn] disk read-only, changes lost on reboot。

[10] passwd [user]
    不带参数改自己的密码；root 可用 passwd <user> 改他人。
    两次输入 New password: / Retype new password:（均回显 *），
    一致才更新；普通用户指定他人时打印红色 Permission denied.
    更新后同样尝试写入 LBA 200-207，失败时追加黄字只读警告。
    注意：成功文案仍是 "password updated (RAM only, reset on reboot)."
    —— 该行属既有输出，按「只添加不修改」未改动，实际行为以是否出现
    只读警告为准（无警告即已落盘）。

[11] color
    8 行 x 2 列一次展示 16 种前景色，含编号、色名与 ######## 色块；
    黑色格改用浅灰背景以便可见。

[12] reboot
    打印黄色 Rebooting zh_OS ... 后向 8042 键盘控制器端口 0x64 写 0xFE
    复位 CPU；QEMU 加 -no-reboot 时虚拟机会直接退出。

[13] shutdown
    打印黄色 System halted. 后 cli; hlt 停机。
    尚无 ACPI/APM 电源管理，不会真正断电，需在 QEMU 终端按 Ctrl+C 退出。

[14] meminfo [test]
    无参数: 绿标题 + 浅灰数据，显示 pool / used / free / blocks，
            初始为 used=0、free=2097152（2MB）；剩余 < 10% 时追加亮黄警告。
    带 test : 跑一组 kmalloc/kzalloc/kfree 自测，打印各阶段 used/free/blocks，
            验证相邻块合并、重复 free、越界指针与超大分配的亮红报错，
            最后把堆还原为初始状态。

[15] uptime
    输出 "up X hours, Y minutes, Z seconds"，文字标签黄、数字绿。
    秒数来自 PIT 100Hz 的 pit_ticks / 100，随运行时间增长。

[16] date
    输出 "YYYY-MM-DD HH:MM:SS"，日期亮黄、时间绿。
    读取 CMOS RTC（端口 0x70/0x71），处理 BCD/二进制模式与 12/24 小时位。
    不处理时区、夏令时、闰秒；RTC 通常是 QEMU 固件 UTC 时间。

[17] dmesg [test]
    无参数: 亮青标题 "=== kernel log ===" + 按最旧→最新打印内核日志环，
            每行含 tick（亮青）与内容（浅灰）；启动日志 tick 多为 0，
            运行期日志带 PIT tick。环满 128 条后覆盖最旧。
    带 test : 写入 139 条编号日志 + 1 条格式化自测（%s/%d/%u/%x/%c/%%），
            共 140 条灌满 128 槽，验证覆盖顺序与回绕正确。

[18] cpuinfo
    亮青标题 "=== CPU Information ==="，依次输出:
      Vendor ID  —— 厂商字符串（GenuineIntel / AuthenticAMD 等，黄字），来自 leaf 0
      Brand String —— 型号（如 QEMU Virtual CPU version 2.5+，浅灰）；
            若 CPU 不支持扩展 leaf 0x80000004 则黄字 "Brand string not supported"
      Family / Model / Stepping —— 按 Intel SDM 公式解析 leaf 1 的 EAX（亮绿）
      Features  —— 11 项特性 4 个一行对齐：FPU/MMX/SSE/SSE2/SSE3/SSSE3/SSE4.1/SSE4.2/
            AVX/AES/64BIT；支持的亮绿、不支持的深灰
      Logical processors —— leaf 1 EBX[23:16]，0 时按 1 计（亮青）
    全部数值用自实现整型转十进制打印，不链接 libc。


----- ramfs 内存文件系统（19-25，B 组第 1 个功能）-----

 路径规则:
   绝对路径 / 开头；相对路径基于当前工作目录（. 与 .. 有效）；
   最多 8 段路径组件、单节点上限 32 个子项。所有节点由内核堆（kmalloc）
   动态创建，重启后清空，不落盘。
   初始树: /、/root、/home、/home/zh、/home/zh/readme.txt（非空示例文件）。

 权限规则:
   root 可在整个树内读写；普通用户只能在自己的 home 子树（/home/<name>）
   内创建与删除，越界时打印红色 Permission denied（ramfs 层返回 -EPERM）。
   cat / ls 等只读操作不受此限制。

[19] ls [path]
    缺省列当前目录，每行 4 个条目：
      目录 —— 亮蓝 + 结尾 "/"；文件 —— 浅灰 + 文件名 + 十进制大小；
      非空 .sh 文件 —— 亮绿（可执行示意）。
    路径不存在红字 "ls: no such file or directory"，
    目标是文件时红字 "ls: not a directory"。

[20] cd <path>
    切换当前工作目录（ramfs_chdir），成败即时反映到提示符的路径段。
    无参数红字 "usage: cd <path>"；目标非目录红字 "cd: not a directory"。

[21] pwd
    输出当前目录绝对路径（绿字），如 /home/zh。

[22] cat <file>
    按 ramfs 内容打印文件；超过 4096 字节截断并追加黄字 truncated。
    目标是目录时红字 "cat: is a directory"。
    静态 4096 字节缓冲，不占内核栈。

[23] mkdir <path>
    新建目录，成功绿字 "mkdir: created"；已存在红字 "already exists"。

[24] touch <path>
    新建空文件，成功绿字 "touch: created"；已存在亦报已存在。
    [M24] 路径落在挂载点里（如 /mnt/x）时改走 VFS，写进 ext2，输出换成
    "created /mnt/x  (inode N)"（N 是 alloc_inode() 真分配到的 inode 号）。

[25] rm <path>
    删除文件或空目录，成功绿字 "rm: removed"；
    目录非空红字 "directory not empty"；普通用户越界红字 Permission denied。
    [M24] 路径落在挂载点里时改走 VFS 的 unlink，释放块与 inode，输出
    "removed /mnt/x  - N blocks freed"；文件不存在红字 "rm: no such file or directory"。


----- ATA 磁盘信息（26，B 组第 2 个功能）-----

[26] diskinfo
    亮青标题 "=== Disk ==="。
    有盘（主通道 0x1F0 的 master 通过 IDENTIFY 0xEC）:
      绿字 ATA primary master: present
      浅灰 persist sectors: LBA 200-207
    无盘:
      黄字 no ATA disk detected
      浅灰 run QEMU with -hda disk.img to persist users
    该命令只反映硬件检测结果，不修改任何状态。


----- 用户态 / 系统调用 / 物理内存（30-32，M1-M3）-----

 说明:
    M1 打开 ring3：GDT 扩到 7 项（用户代码 0x18 / 用户数据 0x20 / TSS 0x28），
    TSS.RSP0 指向专用的 16KB 内核栈，用户窗口是 512 个连续、2MB 对齐的物理帧
    （M3 起由页帧分配器提供，不再是 .bss 里的静态数组）。
    M2 加 int 0x80（IDT 门属性 0xEE = DPL 3），ABI 贴近 Linux i386 老习惯：
    rax=调用号，rdi/rsi/rdx=参数，返回值写回 rax。已实现
    sys_write(1) / sys_ticks(2) / sys_exit(3) / sys_cpl(4)。
    M3 解析 Multiboot2 内存图（tag 6，缺失时退回 tag 4），用
    1 bit = 1 帧（4KB）的位图管理物理内存：先整张标占用，再把 available
    放出来，最后收回低 1MB / 内核映像 / 位图自身 / multiboot2 信息结构。

[30] ring3
    先往用户窗口里铺一段机器码：两次合法写入（窗口 U=1，写得动）→
    pause/loop 空转（这段时间被 PIT 以 100Hz 反复打断，验证 TSS.RSP0 换栈）
    → 往 0xB8F34 写 'X'（该 2MB 大页 U=0，必然 #PF）。
       预期: 亮红 KERNEL PANIC: Page Fault (#PF)
             error code = 0x7 (present + write + user)
             cr2 = 0xb8f34    rip = 用户代码 + 25
             cs = 0x1b (RPL 3)  ss = 0x23
             绿字 ">> fault came from RING 3 (CPL=3): privilege level works."
    说明: 这是"故意让它崩"的自检（M3 阶段还没有进程，用户态出错只能停机）。

[31] syscall
    M2 的双向路径：保存内核现场 → iretq 进 ring3 → 用户程序 int 0x80 →
    sys_write 由内核代印一行 → sys_cpl 返回 3 → sys_exit 触发 usermode_resume
    把 rsp 拨回保存点直接 ret 回 Shell（不 panic）。
       预期末行: 绿字 "M2 PASS: ring 3 -> int 0x80 -> kernel -> sys_exit -> shell"
       同时会看到: 越界缓冲被拒（buf 不在用户窗口内返回 -1）、
                   res[2] caller cpl = 3。

[32] memmap [test]
    无参数打印两部分:
      1) Physical memory map (Multiboot2 tag 6 / E820):
         base / length / type（available, reserved, acpi-recl, acpi-nvs, bad-ram）
         每行末给 MB 或 KB（不足 1MB 用 KB，避免把 1KB 的洞显示成 1MB）
      2) Frame allocator (bitmap, 1 bit = 1 frame = 4 KB):
         total RAM / used / free / 内核映像范围
    帧上限只按"最高的一段 available 内存"算（不按整张图最高地址算）：
    PC 的 E820 常在 4GB 附近报一大段 reserved 空洞，按它算会得出
    total=4096MB、used 上百万帧的假数据。
    memmap test 跑 mm/phys.c 的自测：单帧/连续/2MB 对齐/清零校验，
    以及两类必须被拒的负例（不对齐释放、重复释放），最后校验 used 回到初值。
    那两行亮红是故意的负例，随后绿字 PASS。

[33] taskrun [fault]
    M4 的核心验收：造两个 ring3 任务（A 打绿色 'A'、B 打青色 'B'），
    每个任务有自己的 2MB 用户窗口和 8KB 内核栈，由 IRQ0 每 2 tick (20ms)
    强制换人，所以屏幕上是 BABABABA... 的交错输出。
    现场会先打印 quantum / 两个任务的 pid、窗口基址、内核栈顶，然后:
      -- now running: expect A and B to interleave --
      BABABABABABABABABABABABAback in ring 0: ...
      Task table (M4 preemptive round-robin):
        PID  NAME  STATE    TICKS  SWITCH  RESULT
        0    A     DEAD      25    13      exit 0
        1    B     DEAD      24    13      exit 0
        context switches: 26   tasks created: 2
      M4 PASS: two tasks ran interleaved, both exited normally
    taskrun fault：让 B 打 5 个字母后故意往 0xB8000 写一个字节（ring3 碰显存 = #PF），
    内核只杀掉 B 并换 A 继续跑，不 panic 整机：
      [task] killed: pid=1 name=B vector=14 rip=0x600021 cr2=0xb8f34
      ....(that task only; the machine keeps running)
      AAAAAAAback in ring 0: ...
      M4 PASS: only the faulting task died, the other one kept running
    要点: 换人前必须重写 TSS.RSP0；帧地址取"最后一次被换出时的 r"；
    zh_sched_enter 之前必须 cli（否则时钟会把引导帧踩坏）。

[34] tasks
    打印 TCB 表：PID / NAME / STATE(READY|RUNNING|DEAD) / TICKS / SWITCH /
    RESULT（exit 码，或 killed by vector 14 (#PF) at cr2=...）。
    表尾给累计上下文切换次数与创建过的任务数。没跑过 taskrun 时提示先跑它。

[35] vmspace
    M5 的"看得见"入口：把每个进程的页表直接打印出来。
    表头先给 kernel CR3 与当前 CR3（跑完任务后两者应当相等），再给布局说明：
      layout: [0, 1GB) kernel identity 2MB pages (U=0, shared by every process)
              [0x40000000, 0x40200000) private window, 4 KB pages, U=1)
      walk:   PML4[0] -> own PDPT -> [0]=kernel 2MB PD (U=0)
                              -> [1]=own PD -> PD[0]=own PT -> 512 x 4 KB
    然后每个进程一段：
      pid 0  A   cr3=0x...352000
        pml4=0x...352000  pdpt=0x...353000
        pd  =0x...356000  pt  =0x...357000
        mapped pages: 2 of 512
          VA 0x0000000040000000 -> PA 0x0000000000357000
          VA 0x00000000401ff000 -> PA 0x0000000000358000
    两个进程的 VA 都是 0x40000000，PA 却不同（A 是 0x357000，B 是 0x35f000）——
    这就是"同一虚拟地址、不同物理页"，进程隔离的定义。
    想单独检查页表而不进 ring3：taskrun dry（只建进程 + 打印页表 + 自检走表）。

[36] elf
    M6 的主角：内核第一次"装载别人的程序"，而不是自己拼机器码。
      用法1：elf parse   只解析不装载（VGA 只有 25 行，所以单独一条看得清）
      用法2：elf         解析 -> 建进程 + 装载 -> 进 ring3 跑 -> 校验结果

    elf parse 打出来的东西：
      blob size : 4744 bytes, embedded in the kernel image (no file system yet)
      magic     : 7f 45 4c 46 (\x7fELF)   class=2 (2=ELF64)
      data      : 1 (1=little endian)    version=1
      type      : 2 (2=ET_EXEC)  machine=62 (0x3e=EM_X86_64)
      entry     : 0x40000000
      phoff     : 0x40   phnum=2   phentsize=56
      phdr 0     : type=1 PT_LOAD  flags=5 (R-X)
                  vaddr=0x40000000  filesz=0x65  memsz=0x65
      phdr 1     : type=0x6474e551 PT_GNU_STACK (ignored)

    elf 的完整流程（一屏能看全）：
      load:
        PT_LOAD segments : 1   pages mapped: 1 (4 KB each)   .bss: 0
        entry            : 0x40000000   user stack: 0x401ffff0
        pid              : 0   cr3: 0x355000
      run (ring3, rip = e_entry, own CR3, own stack):
      hello from a real ELF64 binary (M6)
      [kernel] sys_write: 36 bytes delivered for ring 3
        after run        : state=DEAD  exit code=42  ticks=0  fault vector=0
      M6 PASS: ...

    这个程序是 user/hello.c 用 gcc 编出来的真 ELF64（不是内核拼的字节）：
      gcc -m64 -ffreestanding -fno-pie -no-pie -nostdlib -O2 -c user/hello.c
      ld -m elf_x86_64 -T user/user.ld -o build/hello.elf ...
    装载地址 0x40000000 来自 user/user.ld，等于 M5 的进程私有窗口起点。
    build.sh 再用 `ld -r -b binary hello.elf` 把整个 ELF 嵌进内核镜像
    （相当于 Linux 的 initrd），符号名 _binary_hello_elf_start/_end/_size。

    装载器支持的子集（kernel/elf.c）：
      ET_EXEC + EM_X86_64 + PT_LOAD；无重定位、无动态链接、无 PT_INTERP。
      逐段 -> 逐页 vmm_probe() -> 没有就 phys_alloc_frame() + vmm_map_4k()
      -> 拷 p_filesz 字节 -> 清零 .bss -> rip = e_entry。

    失败时会打印具体原因，例如：
      not an ELF file (bad magic)
      not ET_EXEC (no PIE/dynamic support yet)
      entry point outside the user window
      PT_LOAD outside the user window
      out of physical frames while loading

    验收脚本：bash build/qemu_verify_elf.sh（3 屏：提示符 / elf parse / elf）
              关键行应出现 "M6 PASS" 与 "exit code=42"。

    ---- elf fork（M7：fork / wait）----
    跑的是另一个嵌入程序 build/forkdemo.elf（源文件 user/forkdemo.c）：
      用法：elf fork
    一屏能看全的输出：
      M7 fork/wait demo: loading an ELF that forks and waits
        blob      : 6688 bytes  load      : segments=1  pages=1  .bss=1
        entry     : 0x00000000400001a0   stack top 0x00000000401ffff0
      M7 fork/wait demo: started in pid 0
      [kernel] fork: pid 0 -> pid 1  copied pages=2  child cr3=0x360000
        [parent] fork returned child pid 1
      [kernel] wait: pid 0 blocks until pid 1 exits
        [child 1] pid=1 forked, touching my own copy of g_counter
        [child 1] g_counter=5 -> exiting with 11
        [parent] wait() -> 11   (child 1 collected)
        [parent] my g_counter is still 0 -> the child's write did NOT leak
      [kernel] fork: pid 0 -> pid 2  copied pages=2  child cr3=0x368000
        [child 2] pid=2 exiting immediately with 22
      [kernel] wait: pid 0 collected exit code 22 from pid 2
        [parent] wait() -> 22   (child 2 collected)
        after run        : state=DEAD  exit code=0  forks=2  waits=2  faults=0
      M7 PASS: ...

    它验证的正是 Linux fork 的语义：
      - fork() 之后有两个执行流，都从 int 0x80 的下一条指令继续；
        父进程 rax = 子进程 pid，子进程 rax = 0（复制 pt_regs 后把 ax 置 0）；
      - 地址空间是整页复制的（copied pages=2 = 代码页 + 栈页），子进程把全局变量
        加到 5，父进程读到的仍是 0 —— 内存没有共享；子进程的 cr3 与父进程不同；
      - 第一次 wait() 走"阻塞"路径：父进程进 TASK_WAIT 让出 CPU，被换回时
        rax 已经是子进程的退出码（由 notify_parent() 写进父进程保存的中断帧）；
      - 第二次 wait() 走"僵尸"路径：子进程先死、父进程后收尸，直接取走退出码。

    新增系统调用号：FORK=7、GETPID=8、WAIT=9（kernel/syscall.h）。
    验收脚本：bash build/qemu_verify_fork.sh（3 屏：提示符 / elf fork / elf 回归）
              关键行应出现 "M7 PASS" 与 "forks=2  waits=2"。

    ---- elf exec（M8：exec + 按路径装载）----
    先看程序变成了文件：
      ls /bin
        -> execdemo.elf 5496   forkdemo.elf 6688   hello.elf 4744
    这三个 ELF 是启动时由 fs/initrd.c 从内核镜像里铺进 ramfs 的（相当于 Linux 的 initrd）；
    /bin 按 Linux 惯例对所有人可读（ramfs 没有 mode 位，按"根下 bin 子树"判断），
    所以普通用户 zh 也能执行。

      用法：elf exec
    它做的事：从 ramfs 按路径打开 /bin/execdemo.elf -> 建进程 -> 该进程自己
    exec("/bin/hello.elf") -> 同一个 pid 里跑的就是 hello 了。
      一屏输出：
        M8 exec demo: load /bin/execdemo.elf from ramfs, it will exec /bin/hello.elf
          opened    : /bin/execdemo.elf  5496 bytes  (read by path, no fd table yet)
          created   : pid 0  entry 0x00000000400000c0  pages 1
        run: the process will print its pid, then replace itself via exec()
        exec demo: pid 0 is about to exec /bin/hello.elf
                   (this process image is about to be replaced)
        [kernel] exec: pid 0 image replaced (fresh address space)
        [kernel] exec: entry=0x0000000040000000 cr3=0x0000000000382000
        hello from a real ELF64 binary (M6)
          after run        : pid 0  state=DEAD  exit code=42  execs=1  faults=0
        M8 PASS: ...

    它验证的是 exec 的语义：
      - ELF 是按**路径**从文件系统读的（不再是内核里某个 blob 的符号地址）；
      - 同一个 pid 的映像被整体换掉：TCB 的 space/cr3/entry/stack_pa 全换成新的，
        并把中断帧的 rip 改成 e_entry、rsp 改成新栈顶、通用寄存器清零 ——
        于是 int 0x80 返回后那条 iretq 直接落在新程序入口，旧程序再也回不来；
      - 退出码 42 是 hello 给的（execdemo 失败会退 9），说明跑着的确实是新映像；
      - 成功时 exec **没有返回值** —— 因为"调用 exec 的那段代码"本身已被替换掉，
        这正是 exec 和 fork 最大的区别（fork 返回两次，exec 一次都不返回）。

    实现：kernel/syscall.c 的 sys_exec()（逐字节拷路径 + ramfs_read_file + 64KB 内核缓冲）
          kernel/task.c 的 task_exec_current()（新地址空间 + elf_load_into + 改中断帧 + mov cr3）
    新增系统调用号：EXEC=10（kernel/syscall.h）。
    已知限制：没有 argv/envp、没有 fd 表、没有权限位、没有 PT_INTERP，
              且 exec 换下来的旧地址空间不回收（每 exec 一次泄漏一套页表 + 几页）。
    验收脚本：bash build/qemu_verify_exec.sh（3 屏：ls /bin / elf exec / elf fork 回归）
              关键行应出现 "M8 PASS" 与 "exec: pid"。

[37] fd（M9：每进程 fd 表）
    用法：fd
    做的事：从 ramfs 装载 /bin/fddemo.elf 建进程，然后**用户程序自己**去打开文件。
    内核只提供三个门：OPEN(11) / READ(12) / CLOSE(13)；真正维护状态的是 TCB 里的 fd 表
    （ZH_MAX_FDS=8 项，每项 = { 用了没, 指向哪个 ramfs 节点, 读偏移 }）。
    一屏输出：
      fd demo: I am a ring3 program, I will open/read/close myself
        open("/bin/hello.elf") -> fd 0
        read(fd, 4) -> 4 bytes: 7f 45 4c 46
        ^ 7f 45 4c 46 = ELF magic, the fd really reached the file
        read(fd, 4) again -> 4 bytes: 02 01 01 00  (offset moved, not the magic again)
        close(fd) -> 0
        read(fd) after close -> -1 (fd is dead, as expected)
        open("/bin/nope.elf") -> -1 (no such file)
        open("/bin") -> -1 (it is a directory, not a file)
      fd demo: all five checks passed
        fd table of the process (ZH_MAX_FDS=8):
          open ok=1  open denied=2  read=2  close=1
        after run        : state=DEAD  exit code=0  faults=0
      M9 PASS: ...

    它验证的是 fd 的语义（与 Linux 对齐的三点）：
      - fd 是**下标**不是指针：用户只拿到 0、1、2…，越界/伪造的 fd 一律 -1；
      - 读偏移挂在 fd 上（相当于 struct file 的 f_pos），所以第二次 read 读到的是
        魔数之后的字节，而不是又从头读一遍；
      - close(fd) 之后同一个 fd 立即失效（再 read 返回 -1）；
      - open 一个目录 / 一个不存在的路径都会失败（类型与存在性检查在 ramfs 里做）。
    另外 fork 出来的子进程会继承父进程的 fd 表（file_table_clone），
      与 Linux"fork 后父子共享已打开文件"的最小版本一致。
    程序自检五项全过才 exit(0)；`fd` 命令再按内核计数器（open ok / denied / read / close）
      二次核对，两边对不上就判失败 —— 用户说"我读到了"必须和内核说"你确实读过"一致。
    已知限制：只读（没有 creat/write/unlink）、没有 dup/pipe/lseek、没有 O_* 标志位，
      sys_write 仍然只写屏幕。
    验收脚本：bash build/qemu_verify_fd.sh（3 屏：ls /bin / fd / elf exec 回归）
              关键行应出现 "M9 PASS" 与 "open ok="。

[38] wr（M10：可写文件）
    用法：wr
    做的事：从 ramfs 装载 /bin/wrdemo.elf，然后**用户程序自己**建文件、写文件、读回来。
    新增系统调用：CREAT(14) / FWRITE(15) / UNLINK(16)。
      - creat：父目录可写才允许；不存在就建、存在就清空（等价 Linux creat(path,0666)）。
      - write：追加写（ramfs_node_append 重新分配 + 拷旧 + 接新 + 释放旧），
        所以内容真的进了文件系统，别的进程 open 能读到。
    一屏输出：
      wr demo: a ring3 program creates and writes a real file
      [kernel] creat: /home/zh/m10.txt -> fd 0
        creat("/home/zh/m10.txt") -> fd 0
      [kernel] write: 30 bytes appended to fd 0
        write(fd, 30 bytes) -> 30
      [kernel] write: 38 bytes appended to fd 0
        write(fd, 38 bytes) -> 38   (appended, the file grew)
        close(fd) -> 0
        open("/home/zh/m10.txt") again -> fd 0
        read back -> 68 bytes:
      hello from a ring3 file write
      this line was appended by the same fd
      wr demo: the bytes read back are exactly the bytes I wrote
        after run        : state=DEAD  exit code=0  faults=0
        fs counters      : creat=1  writes=2  bytes=68  opens=1
      M10 PASS (files): ...
    PASS 之后紧接着在同一次开机里执行 `cat /home/zh/m10.txt`，应当看到同样两行 ——
      这证明内容留在 ramfs 里，而不是程序自己的内存里。

[39] spawn（M10：fork -> exec -> wait）
    用法：spawn
    做的事：装载 /bin/spawndemo.elf，由用户程序完成 Linux shell 执行一条外部命令的三步：
      pid = fork();
      if (pid == 0) exec("/bin/hello.elf");   // 子进程换成新程序（连 mm 一起换）
      else          wait(&code);              // 父进程进 TASK_WAIT，等退出码
    一屏输出：
      spawn demo: pid 0 will fork, the child will exec, the parent will wait
      [kernel] fork: pid 0 -> pid 1  copied pages=2  child cr3=0x00000000003ad000
      [parent] fork returned child pid 1
      [kernel] wait: pid 0 blocks until pid 1 exits
      [child ] fork returned 0, I am pid 1, now replacing myself with hello.elf
      [kernel] exec: pid 1 image replaced (fresh address space)
      [kernel] exec: entry=0x0000000040000000 cr3=0x00000000003b3000
      hello from a real ELF64 binary (M6)
      [parent] wait() -> 42   (child 1 collected)
      spawn demo: fork -> exec -> wait closed the loop in one process tree
        after run        : state=DEAD  exit code=0  faults=0
        kernel counters  : forks +1  execs +1  waits +1
      M10 PASS (processes): ...
    看点：两处 cr3 不同（fork 给子进程一套、exec 又换一套），说明"子进程的地址空间"
      与"父进程的地址空间"是两回事；而父进程拿到的 42 是 hello 的退出码 —— exec 之后
      新映像的 exit 才算数。
    验收脚本：bash build/qemu_verify_m10.sh（4 屏：wr / cat / spawn / fd 回归）
              关键行应出现 "M10 PASS" 与 "wait() -> 42"。
    已知限制：没有 argv/envp（exec 只能带路径），没有信号（父进程只能 wait），
      没有 dup/pipe/seek，没有 inode 权限位。


----- FAT16 只读挂载（27-29，B 组第 3 个功能）-----

 说明:
    独立的只读文件系统视图，与 ramfs 各走一套命令（ls/cat 仍属 ramfs，
    fatls/fatcat 才访问 FAT16），互不覆盖、互不干扰。
    读的是主通道的第二块盘（QEMU: -drive file=data.img,format=raw,if=ide,index=1），
    只支持 8.3 短文件名（不解析 LFN），名字匹配大小写不敏感，
    显示时按 FAT 规范输出大写。不支持写、mkdir、rm。

[27] fatmount
    读 LBA 0 解析 BPB（0x0B 字节每扇区 / 0x0D 扇区每簇 / 0x0E 保留扇区 /
    0x10 FAT 数 / 0x11 根目录项数 / 0x16 FAT 大小 / 0x1C 分区前扇区 / 0x2C 根簇号），
    校验每扇区 512 字节、每簇为 2 的幂、0x36 处为 "FAT16   "（或簇数落在
    4085..65525 推断），成功后缓存 FAT / 根目录 / 数据区起始 LBA。
       成功: 绿字 fat16 mounted
       失败: 红字 fatmount: <原因>
             无盘            -> no disk on primary slave
             类型不符        -> not a FAT16 filesystem
             BPB 非法        -> invalid BPB
             读扇区失败      -> I/O error

[28] fatls [path]
    未挂载时红字 "not mounted, run fatmount first"，需先执行 fatmount。
    缺省列根目录，每行 4 个条目：目录亮蓝 + "/"，文件浅灰；
    跳过卷标、长文件名项以及 . 与 .. 两个伪目录（子目录列表同样过滤）。
    支持根目录与一层子目录（最多 4 段路径）。
    错误: no such file or directory / not a directory / I/O error。

[29] fatcat <path>
    按簇链（FAT 项跟随，>=0xFFF8 视为链尾）读取并打印文件内容，
    超过 4096 字节截断并追加黄字 truncated。
    无参数红字 "usage: fatcat <path>"；目标是目录时红字 "is a directory"。
    8.3 名大小写不敏感，fatcat /hello.txt 与 /HELLO.TXT 等价。

 其它提示:
    未知命令 -> 亮红 "zh_OS: command not found: <cmd>"
                亮黄 "Type 'help' for a list of commands."
    权限不足 -> 亮红 "Permission denied."


四、构建与运行命令（WSL2 Ubuntu，不生成任何 .bat）
--------------------------------------------------------------------------------
 在 Windows 11 以管理员身份打开 PowerShell，只做一次:
   wsl --install -d Ubuntu

 进入 WSL 后:
   cd ~/zh_OS
   ./setup.sh                 # 首次：安装依赖并写入 env.mode
   ./check.sh                 # 只读体检：打印 gcc/nasm/grub-mkrescue/xorriso/qemu 版本
   ./build.sh                 # 编译内核并用 grub-mkrescue 生成 zh_OS-0.2beta.iso

 三种启动方式（按需选择）:
   # 1) 最小启动：无磁盘，账户走内存态
   qemu-system-x86_64 -cdrom zh_OS-0.2beta.iso -m 128

   # 2) 用户表持久化：再挂一块可写磁盘
   dd if=/dev/zero of=disk.img bs=1M count=16
   qemu-system-x86_64 -cdrom zh_OS-0.2beta.iso \
     -drive file=disk.img,format=raw,if=ide -m 128

   # 3) 再加一块 FAT16 数据盘（主通道从盘 index=1）
   ./build/mkfat16_img.sh      # 生成 32MB data.img，含 hello.txt / zh.txt / sub/
   qemu-system-x86_64 -cdrom zh_OS-0.2beta.iso \
     -drive file=disk.img,format=raw,if=ide \
     -drive file=data.img,format=raw,if=ide,index=1 -m 128

 校验新代码是否编进内核:
   strings build/zh_OS.elf | grep -E 'Welcome back|built-in commands|fat16 mounted|ATA primary'

 把 ISO 复制到 Windows 桌面（供 VirtualBox / VMware 使用）:
   cp zh_OS-0.2beta.iso /mnt/c/Users/你的用户名/Desktop/

 可选编译开关:
   ZH_VGA_SELFTEST=1 ./build.sh    # 编入启动时的 16 色前景自检（默认关闭）

 常用验收流程（QEMU 内）:
   login: zh / Password: zh
   help / color / uname / whoami / uptime / date / meminfo / dmesg / cpuinfo
   ls / cd /home/zh / pwd / cat readme.txt / mkdir tmp / touch a.txt / rm a.txt
   diskinfo                    -> 有盘绿字 present / 无盘黄字 no ATA disk detected
   fatls                       -> 未挂载红字提示
   fatmount / fatls / / fatcat /hello.txt / fatls /sub
   useradd test                -> 普通用户红字 Permission denied.
   su root / Password: zh       -> 提示符变红 #
   useradd test                -> 绿色创建成功（有盘时无只读警告）
   passwd                       -> 改自己的密码
   logout -> login: test / Password: zh -> 绿色 Welcome back, test!
   重启后（挂 disk.img 时）test 仍可登录，改过的密码仍生效

 无头回归脚本（build/，不参与编译）:
   build/qemu_dump_ramfs.sh        # ramfs 七命令逐屏
   build/qemu_dump_ata.sh [no|hdd]# 无盘 / 有盘两种持久化场景
   build/qemu_dump_ata_passwd.sh   # 改密跨重启
   build/qemu_verify_ata_regress.sh# cpuinfo/ramfs/历史键/logout 回归
   build/qemu_dump_fat.sh          # FAT16 十屏验收
   build/qemu_verify_fat_regress.sh# 全量回归
   python3 build/parse_vga.py <dump.log> 'label1,label2'   # 渲染 xp 导出的 VGA 文本


五、注意事项
--------------------------------------------------------------------------------
 * 改动任何源码后必须重新执行 ./build.sh，旧 ISO 不会自动更新。
 * 账户表默认内存态；只有挂载可写磁盘时才会从 LBA 200-207 读回并写回。
 * ramfs 全内存态，重启清空，不落盘；FAT16 是只读挂载，两者互不影响。
 * 没有用户态、进程、SMP、定时器时间戳之外的调度；Shell 运行在 ring 0。
 * VGA 文本模式为 CP437，屏幕上的内核输出必须是 ASCII；中文只出现在注释与文档中。
 * 已知限制的完整列表见 README.md「已知限制」一节。

[40] argv（M11：exec 携带 argc/argv）
--------------------------------------------------------------------------------
  作用：父进程 fork 出子进程，子进程 exec 同一个程序但带三个参数
        {"argvdemo","alpha","beta"}；新映像的 _start(argc, argv) 把 argc 与每个
        argv 打印出来再 exit(0)。父进程 wait 收到 0。

  内核做了什么（M11 的核心）：
    1) sys_exec 现在是 (path, argv_ptr, argc)：先读用户态的指针数组（每个指针
       都过 user_ptr_ok），再逐字节把每个字符串拷进内核 g_exec_args[8][97]；
    2) task_exec_current_argv() 建新地址空间 + 新栈页后，把字符串写进新栈页的
       底部（页帧恒等映射，所以直接按物理地址写），指针值用虚拟地址；
    3) 指针数组 16 字节对齐接在字符串后面，末尾一个 NULL；
    4) 改中断帧：rip=新入口、rsp=新栈顶、rdi=argc、rsi=&argv[0]；
    5) argv=NULL 时等于老的 exec(path)，老程序不受影响。

  顺带修掉的两个内核必修项（都不是程序写错）：
    * CR4.OSFXSR / OSXMMEXCPT 没开 —— ring3 执行 gcc 自动向量化出的 SSE 指令
      （movq (%rip),%xmm0 / movaps）会直接 #UD（vector 6）；
    * 用户栈顶 16 对齐 —— gcc 假定函数是被 call 进来的（入口 rsp ≡ 8 mod 16），
      对齐不对 movaps %xmm0,(%rsp) 就是 #GP（vector 13）。栈顶改成 SPAN-8。

    [parent] wait() -> 0

[41] mm（M12：地址空间回收）
--------------------------------------------------------------------------------
  作用：证明 exec 换下来的旧 mm 真的被销毁了。跑 /bin/reexec.elf，它靠 argv
        把"剩余深度"传下去，连续 exec 自己 7 次 —— 每次都建一整套新 mm。
        命令对比运行前后的页帧空闲数：如果回收缺失，7 次要吃掉 40 多帧。

  内核做了什么（M12 的核心）：
    1) 新增 vmm_space_destroy()：扫私有窗口那一个 PT 的 512 项，把每个
       PRESENT 项背后的用户页归还分配器；
    2) 再把 PT / PD / PDPT / PML4 这四帧自己也归还（最容易漏的就是这四帧）；
    3) 回收点一：exec 换完 CR3 之后销毁旧空间（顺序不能反，否则 #PF、CR2
       等于刚释放的地址）；
    4) 回收点二：命令之间的 task_reset() 统一回收所有残留任务的 mm。

  预期输出（关键行）：
    frames    : total=32736  used=3015  free=29721
    [reexec] pid 0: depth 6  -> exec myself with 5
    ...
    [reexec] pid 0: depth 0 reached, no more exec. exiting 0
    after run : total=32736  used=3023  free=29713
    execs     : +6   reclaimed: +6 mm / +12 pages
    free      : before=29721  after=29713  delta=8
    M12 PASS: every exec() destroyed the mm it replaced.

  读法：delta=8 就是"最后一个还活着的进程那一套 mm"，与 exec 次数无关；
        再跑一次 mm，delta 变 6、终点仍是 29713 —— 账稳、不累积。

  注意：第一次跑 mm 曾经报 "leaked 2056 frames"，那不是漏洞而是测量点错了 ——
        task_init() 第一次调用会一次性分配 8MB 用户窗口池（2048 帧），
        命令现在先 task_init() 再开始量账。

  验收：bash build/qemu_verify_m12.sh     -> build/m12_verify/（3 屏）
        全量回归 bash build/regress_all.sh  -> M2 … M12

[43] cow（M15：写时复制 fork）
--------------------------------------------------------------------------------
  作用：跑 /bin/cowdemo.elf，然后用三个计数器把"fork 到底付了什么钱"摆出来。

  机制：fork 不再复制页，只把父进程的帧以"只读 + PTE 第 9 位 COW"映射进子进程，
        并把父进程那一项也改成只读；谁写谁触发 #PF，vmm_cow_fault() 那一刻才
        申请新帧、拷 4KB、改成可写。帧有引用计数，减到 0 才真的回分配器。

  预期输出（关键行）：
    M15 copy-on-write: fork() shares pages, only writes pay for a copy
    [parent] after my write: g_value=0x00005555  writes=0x00000001
    [child ] after my write: g_value=0x0000aaaa  writes=0x00000001
    [parent] after the child is gone, my page still reads 0x00005555
    fork      : shared=2 page(s) mapped read-only+COW  (0 frames copied at fork)
    on write  : copied=4  page fault(s)=4  (only the pages each side wrote)
    M15 PASS: ...

  读法：shared 是 fork 时共享的页数，copied 是"因为有人写才复制"的页数。
        父子都不写 -> copied=0，fork 的用户页成本是 0 帧。

  注意：这条命令会顺带把内核日志关掉（task_set_exec_verbose(0) + syscall_set_write_log(0)），

           i_blocks=0、i_block[] 清零
        4) 位图与计数：块位图/inode 位图清位，组描述符与超级块的空闲计数各 +1

  预期输出：
    removed /big2.txt  inode 18  19 blocks freed

  红字：
    ext2rm: no such file or directory          文件不存在（删第二次就是这句）
    ext2rm: is a directory (rmdir is not supported yet)   暂不支持删目录
    ext2rm: corrupt inode or directory entry   位图里该位本来就是 0（重复释放，拒绝执行）

  验收：bash build/qemu_verify_m23.sh（3 屏 + 宿主侧 e2fsck）
        -> M23 PASS: unlink freed the data blocks, the pointer block and the inode
  最硬的判据：e2fsck -fn 回到 "17/4096 files, 1201/16384 blocks"，与造镜像时完全一致。

[57] videomode（M25：看看内核拿到了什么屏）
--------------------------------------------------------------------------------
  作用：把 Multiboot2 帧缓冲标签（type 8）的信息报出来，顺便算一遍文本行列。
        没有图形模式时红字提示 "text mode 80x25 (no framebuffer from GRUB)"。

  预期输出（QEMU 默认档）：
    framebuffer 1280x800x32  pitch 5120
    text grid 160x50 cells (8x16 font)

  为什么行列是算出来的：图形模式下没有 0xB8000 那套字符发生器，字是内核用
  8x16 点阵字体一个个像素画上去的。列 = 宽/8，行 = 高/16，换分辨率会自动变。

[58] res <W>x<H> [bpp]（M25：运行时改分辨率）
--------------------------------------------------------------------------------
  作用：长模式下已经调不到 int 10h（BIOS 中断只在实模式有），所以直接写
        Bochs VBE dispi 寄存器组（端口 0x1CE 索引 / 0x1CF 数据）改模式：
        先读 ID 确认是 0xB0C0..0xB0C5，再写 XRES/YRES/BPP，最后 ENABLE=0x41。
        ID 不对（真机没有这套接口）就红字拒绝，绝不乱写端口。

  示例：
  分隔符：宽高之间用字母 x（或星号 *），例如 res 1024x768 / res 1024*768。
          文档正文里的 "1280x800" 有时写成 1280×800，那是排版用的乘号，命令不认。
    res 1024x768        32bpp（默认）
    res 800x600 24      指定色深
    res 1280x720

  预期输出（成功时立刻重报几何）：
    framebuffer 1024x768x32  pitch 4096
    text grid 128x48 cells (8x16 font)

  红字：
    res: no framebuffer, this kernel is in text mode
    res: the video device refused that mode
    res: expected <width>x<height>  (x or *)  /  usage: res <width>x<height>

  启动菜单：第 1 项 = 文本模式 80x25（默认，老命令照旧），第 2 项 = 图形模式。
        图形模式用的是单独的 build/zh_OS_fb.elf（同一个源码，只多了帧缓冲请求标签）。

  换模式不再清屏（M26）：内核有一层整屏字符缓冲（每格记 字符 + 前后景调色板号），
        res 之后会把旧屏幕"真正用过的最后几行"搬到新屏幕，再按新几何整屏重绘。
        对齐方式按"装不装得下"定（M27 调整）：历史填满新屏就搬最后整屏（屏满无线），
        装得下就贴顶部、光标紧跟历史最后一行。缓冲只覆盖可见的一屏，
        滚出去的历史还没有 scrollback。

  大分辨率（M27 修复）：换模式前先按新几何补页表（paging_map_2mb_range），
        映射不出来就红字拒绝、不切模式。之前 res 1920X1080 会 #PF(write, not present)
        然后 KERNEL PANIC —— 因为启动时只按 1280x800 映射了约 4MB 帧缓冲，
        1920x1080x32 要 8.3MB，写到 4MB 之后就踩空了。现在是先映射后切模式，
        上限 2560x1600（内核对 w/h 的硬限制），来回换档也不会重复吃页目录。
        实测：res 1920*1080 -> framebuffer 1920x1080x32 pitch 7680 / 240x67，无 panic。

  验收：bash build/qemu_verify_m25.sh
        -> 1280x800（GRUB auto）-> res 1024x768 -> res 800x600
        screendump 的 PPM 尺寸依次是 1280x800 / 1024x768 / 800x600
